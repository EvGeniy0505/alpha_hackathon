# Архитектура и границы MVP

## Компоненты

```mermaid
flowchart LR
    Client[Клиент: веб-кабинет] --> API[Python HTTP API]
    Bank[Аналитик: веб-кабинет] --> API
    API --> Auth[Сессия, роль, владелец]
    API --> Flow[Валидация и переходы]
    Flow --> Checks[Локальные симуляторы компании и БКИ]
    Checks --> Score[Объяснимый балл и показатели]
    Score --> Policy[Отдельная кредитная политика]
    Policy --> Alternative[Подбор и перепроверка альтернативы]
    Flow --> DB[(SQLite: заявки, события, сессии)]
```

Все компоненты в одном процессе/контейнере. Слой правил не зависит от HTTP и БД. Внешние вызовы отсутствуют. Это вертикальный срез процесса, а не банковская платформа.

## Состояния

```mermaid
stateDiagram-v2
    [*] --> draft: клиент сохраняет
    draft --> checking: отправка с согласием
    checking --> approved: политика одобряет
    checking --> rejected: политика отказывает
    checking --> manual_review: нужен сотрудник
    manual_review --> needs_info: банк задаёт вопрос
    needs_info --> checking: клиент отвечает
    manual_review --> approved: решение банка
    manual_review --> rejected: решение банка
    approved --> signed: клиент принимает, имитация
    signed --> funded: имитация выдачи
    funded --> [*]
    rejected --> [*]
```

`checking` и `signed` — короткие синхронные этапы, записываемые в историю. UI получает итог запроса; фоновых очередей и выдуманного ожидания нет.

После уточнения неблокирующий результат снова передаётся человеку. Пояснение клиента само по себе не отменяет просрочку или другой отрицательный факт. Автоматически отклонённую заявку нельзя одобрить через банковский endpoint.

## Данные

| Таблица | Поля | Смысл |
|---|---|---|
| `users` | `username` PK, `password_hash`, `role` | Учётные записи и роль client/bank |
| `clients` | `username` PK/FK → users, `tax_id` UNIQUE, реквизиты, возраст, контакты, средняя выручка, даты | Профиль компании |
| `applications` | `id` PK, `owner`, `status`, `data` JSON, `assessment` JSON, `created_at`, `updated_at` | Последняя версия заявки и расчёта |
| `events` | `id` PK, `application_id` FK, `at`, `status`, `actor`, `note` | Хронология действий |
| `sessions` | `token_hash` PK, `username`, `expires` | SHA-256 токена случайной сессии, срок 8 часов |

Пользователи и профили компаний хранятся в таблицах `users` и `clients`. Начальные данные берутся из `data/clients.json`; пароль сохраняется только как PBKDF2-хеш. Поля анкеты описаны в OpenAPI. JSON выбран для небольшого прототипа; полноценное версионирование анкеты и миграции — следующая итерация.

`assessment` содержит `checks`, `score`, `decision`, `alternative`; после ручного действия добавляется `bank_decision`. Автоматическая оценка и обоснование сотрудника не подменяют друг друга. UI показывает фактический статус заявки и ручное предложение, если оно есть.

## Расчёт

- Свободный поток = выручка − операционные расходы − текущие кредитные платежи.
- Новый платёж — аннуитет по условной ставке выбранного продукта.
- Покрытие = свободный поток / новый платёж. Значение ниже 1 означает недостаток потока; порог автоматического одобрения зависит от продукта: от 1,2 до 2,0; для разового оборотного кредита — 1,5.
- Балл учитывает покрытие, возраст бизнеса и синтетические проверки. Результат правил отдельно ограничивает выдачу при неактивной компании, серьёзной просрочке и других препятствиях.
- Альтернатива перебирает допустимые сроки, вычисляет сумму под порог выбранного продукта и дополнительный запас 0,5 платежа и заново вызывает скоринг и политику. Приоритет: улучшенный статус, максимальная сумма, затем минимальный срок. Это эвристика, а не оптимум стоимости кредита.
- Стресс-тест вызывает `/api/preview` для исходной анкеты и копии со сниженной выручкой. Ни один расчёт не сохраняет заявку.

## Надёжность и доступ

Каждая мутация состояния и её события выполняются в одной SQLite-транзакции `BEGIN IMMEDIATE`. Параллельная повторная отправка/выдача получает 409 после проверки уже изменившегося состояния. Это защита перехода, а не универсальная идемпотентность создания заявки: два отдельных POST создания дадут два черновика.

Клиент читает и меняет только свои заявки. Банк читает все заявки, но принимает решение только на `manual_review`. Редактировать анкету банк не может. Строковые значения передаются в SQL параметрами; браузер экранирует пользовательский текст.

Сессия хранится в HttpOnly SameSite=Strict cookie. На сервере проверяются Host и Origin для записи; CORS не включён. JSON ограничен 64 КиБ. CSP запрещает внешние скрипты и inline-код. Cookie без Secure нужен только для локального HTTP; для размещения по HTTPS политика должна быть изменена.

В комплекте нет полноценных банковских IAM, лимитов входа, очередей, идемпотентного создания, защиты от редактирования в двух вкладках, резервного копирования и мониторинга. SQLite WAL помогает локальной конкурентности, но не делает сервис горизонтально масштабируемым.

## Как проверять

Автоматические сценарии находятся в `tests/`, ручной путь — в README. Обязательно проверить одобрение, отказ, ручное решение и цикл уточнения; отдельно — чужую заявку, двойную отправку, перезапуск и пересчёт без записи.

Следующий инженерный шаг после чемпионата: сохранить контракт и правила, перенести HTTP-слой на эксплуатационный веб-стек, подключить нормальную идентификацию, PostgreSQL при нескольких репликах, аудит версий, мониторинг и адаптеры внешних проверок с тайм-аутами. Изменение стека не требуется для демонстрации локальной MVP.

## Связи данных

```mermaid
erDiagram
    users ||--o| clients : "профиль компании"
    users ||--o{ sessions : "сессии, логическая связь"
    clients ||--o{ applications : "владелец, логическая связь"
    applications ||--o{ events : "история"
    users {
        TEXT username PK
        TEXT password_hash
        TEXT role
    }
    clients {
        TEXT username PK,FK
        TEXT tax_id UK
        TEXT company_name
        INTEGER business_months
        REAL average_revenue_6m
        TEXT contacts
    }
    applications {
        TEXT id PK
        TEXT owner
        TEXT status
        TEXT data_JSON
        TEXT assessment_JSON
        TEXT created_at
        TEXT updated_at
    }
    events {
        INTEGER id PK
        TEXT application_id FK
        TEXT at
        TEXT status
        TEXT actor
        TEXT note
    }
    sessions {
        TEXT token_hash PK
        TEXT username
        REAL expires
    }
```

В ER-диаграмме contacts объединяет поля contact_name, phone, email, legal_address
для компактности; отдельной колонки contacts нет. data_JSON и assessment_JSON
обозначают текстовые колонки data и assessment с JSON.
Явные внешние ключи БД: clients.username → users.username и
events.application_id → applications.id. Связи applications.owner и
sessions.username обеспечиваются логикой приложения.
Карточка заявки получает актуальный профиль компании при чтении, отдельного
неизменяемого снимка реквизитов на момент отправки пока нет.
Исходные CSV остаются на устройстве пользователя; в JSON анкеты сохраняются
имена файлов, источники и рассчитанные числовые показатели.

## Контракты и воспроизводимая проверка

Все 15 маршрутов HTTP API описаны в [OpenAPI](openapi.json).
Сводка доступа, ошибок и действий — в [описании API](API.md).
[Коллекция запросов](requests.http) проходит создание, отправку, получение
предложения, цикл уточнения и ручное решение с действующими аккаунтами.
Тест tests/test_delivery.py выполняет запросы этой коллекции через настоящий
диспетчер Handler и временную SQLite; сетевой HTTP отдельно покрыт tests/test_api.py.

Docker запускает один экземпляр сервера, хранит состояние вне контейнера и
принимает конфигурацию из окружения. HEALTHCHECK проверяет доступность HTTP и SQLite.
Внешние банковские системы и облачные зависимости не нужны.
